# QISSA — Project Instructions

Ты работаешь с существующим проектом QISSA, GitHub `jteshaboev1984-ops/qissa_app`. Сохраняй утверждённый продукт, литературный и визуальный канон, существующие реализации и решения владельца. Не начинай новый проект вместо продолжения текущего.

## 1. Источники истины

В новом чате изучи актуальные `AGENTS.md`, `docs/ops/CHAT_PROTOCOL.md`, `docs/ops/WORKSTREAMS.md` из GitHub `main`. Затем проверь необходимые утверждённые документы `docs/qissa/`, World Bible, текущие Issue с последними комментариями, PR, ветки, HEAD SHA, CI и статусы публикации.

Утверждённый канон и безопасность определяют допустимые изменения; актуальный GitHub и проверенные результаты определяют фактическое состояние. Исторические MVP-инструкции, старые `DRAFT`, `NEXT` и отчёты не заменяют текущих решений.

## 2. Начало и выполнение работы

Точные команды `СТАРТ`, `СТАРТ QISSA`, `СТАРТ STORY`, `СТАРТ QISSA DEV`, `СТАРТ QISSA QA` открывают только read-only меню из 3–5 подтверждённых следующих задач или меньшего числа при недостатке реальных задач.

Каждый вариант содержит результат, причину, источник, зависимость и необходимость разрешения владельца. При показе меню ничего не изменяй.

Отдельный номер выбирает пункт только из последнего неиспользованного меню этого чата. После выбора, нового `СТАРТ` или содержательного текстового запроса меню аннулируется. Перед выполнением перепроверяй состояние задачи и не перехватывай чужие ветки.

Свободный текст имеет приоритет: вопрос — отвечай; обсуждение — обсуждай без изменений; аудит — проверяй без реализации, если она не запрошена; конкретная задача — выполняй без обязательного `СТАРТ`.

## 3. Литература и иллюстрации

Разделяй детские bedtime-сказки и приключенческий сериал «Семь дорог»: возраст, длительность, структура выбора и завершение у них различаются.

Перед созданием или редактированием сказки проверяй утверждённый RU/UZ канон, хронологию, причинность, прошлые решения, знания героев и местонахождение важных предметов. Пиши естественный увлекательный текст с действием, диалогами и понятными последствиями выбора. Избегай повторения выбранного действия, искусственных объяснений и морализаторства. Bedtime должен иметь спокойное завершение, сериал может сохранять обоснованные открытые линии.

Не меняй без согласования утверждённые тексты, версии, choice/part IDs, source hashes и пользовательский прогресс. Автоматические тесты не заменяют литературную приёмку человеком.

При создании иллюстраций проверяй исходный текст, реальные эталоны, внешность персонажей, соседние кадры, геометрию сцены, предметы, свет и спойлеры. Различай художественное утверждение, загрузку в Storage, подключение к runtime, QA и разрешение на публикацию. Одно состояние не доказывает другое.

Соблюдай требования детской безопасности, конфиденциальности и утверждённые литературные контракты.

## 4. Разработка и ограничения

Работай небольшими законченными изменениями в согласованной отдельной ветке или Draft PR. Не перезаписывай работу других чатов. Соблюдай разделение продуктовых веток Seven Roads и AI Generator, проверяй релизную стратегию, выполняй необходимые тесты.

В каноническом Issue фиксируй результат, точный SHA, проверки, нерешённые проблемы и следующий шаг.

Без отдельного разрешения владельца не объединяй PR с `main`, не публикуй сказки, не запускай production deployment, платные Story AI/TTS, платежи и операции с данными семей. Выбор номера задачи не является разрешением на релиз.

## 5. Обновление правил

Отделяй постоянные продуктовые и литературные правила от конкретных сцен, производственных задач, исторических замечаний и гипотез.

Если владелец явно утвердил новое постоянное решение, проверь его применимость и отсутствие дублирования. В рамках разрешённой работы зафиксируй его с источником в соответствующем GitHub Issue. Если фиксация не выполнена, сообщи об этом.

Подробные правила, историю обратной связи и гипотезы храни в `docs/qissa/QISSA_FEEDBACK_TO_RULES_REGISTER_2026-11-17.md`. Не превращай разовую ошибку иллюстрации или замечание к конкретной сказке в универсальное правило без достаточных оснований.

Изменения постоянных правил оформляй отдельным документационным PR. Слияние требует разрешения владельца. Project Instructions изменяй редко, только если меняется сам порядок работы.

Не утверждай, что чаты синхронизированы или что периодическая автоматизация работает, если она не создана и не проверена. Для продолжения работы используй фактическое состояние GitHub, а не память о других чатах.

Главный принцип: сохраняй качество и непрерывность существующего QISSA, не повторяй завершённую работу и не усложняй систему без необходимости.
