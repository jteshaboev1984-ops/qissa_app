# QISSA Split Story Architecture and Series Scaling — September 2026

Status: implementation architecture for post-beta scalability while preserving the current closed-beta bedtime UX.

## Decision

QISSA will not make one model output simultaneously own prose, canon, branch state and safety.

The production direction is:

`compact active memory -> Story Architect -> immutable blueprint -> Narrator -> deterministic validation -> rule safety -> semantic safety + moderation -> publish`

The default high-volume models are GPT-5.6 Luna. A stronger narrator model may be configured later as a rare escalation path, but escalation is disabled by default during tuning.

## Why

Production testing of the previous monolithic StoryCandidate prompt showed that the provider could return valid structured JSON while repeatedly missing independent product constraints such as exact story length or Russian HERO-token grammar. Full retries also allowed prose repair to regenerate state and branch metadata that were already correct.

The split architecture changes ownership:

- Architect owns story goal, causal beats, choices, durable canon, relationship updates and branch consequences.
- Narrator owns child-facing title, prose, choice resolution wording and vocabulary.
- Server assembly owns the final StoryCandidate structure.
- Deterministic validators remain authoritative for hard product constraints.
- Safety remains a publish gate, not a narrator responsibility.

The Narrator cannot create or alter canon/state because those fields are absent from its output schema.

## Runtime stages

### 1. Story Architect

Input:
- age/language/style/mood;
- compact canon;
- relationship state;
- recurring characters;
- active arc;
- last episode summary;
- recent confirmed choices.

Output:
- one central goal;
- setting anchor;
- 4-8 causal beats;
- continuity callbacks;
- Episode 1 decision point and exactly two branch contracts, or zero choices for Episode 2;
- top-level state patch;
- branch-only state patches;
- next-session preview when applicable.

Architect output is internal planning data, not story prose.

### 2. Narrator

Input:
- immutable blueprint;
- language/age/style;
- hard story word range.

Output only:
- title;
- story_text;
- resolution_text for blueprint choices;
- vocabulary.

Narrator may add ephemeral dialogue, sensory details, reactions and humor, but may not introduce new durable lore.

### 3. Deterministic repair

If the assembled candidate fails only story/resolution length gates, the existing targeted text repair is allowed. State/canon/choice contracts remain immutable.

A non-length narration failure may later use a configured stronger Narrator model against the SAME blueprint. It must never trigger a new Architect plan automatically.

### 4. Safety

After deterministic validation passes:
- rule-based safety runs locally;
- semantic safety and OpenAI moderation run as publish gates;
- moderation remains separate from story generation.

## Model routing

Default:
- Architect: GPT-5.6 Luna;
- Narrator: GPT-5.6 Luna;
- Safety classifier: GPT-5.6 Luna;
- Moderation: omni-moderation-latest.

Optional future escalation:
- only the Narrator is escalated;
- blueprint/canon is never regenerated by escalation;
- escalation should be driven by measured failure rates or a premium quality tier, not used on every story.

## Cost principle

Splitting does not mean many sequential agents. The normal paid path should stay close to:

1. short Architect call;
2. Narrator call;
3. short safety classification after deterministic validation.

Moderation is independent. Repair/escalation is exceptional and observable.

Static instructions should remain stable to benefit from provider prompt caching.

## Bedtime session vs long-running series

These are different concepts and must remain separate.

A **bedtime session** keeps the current child UX:

`Segment 1 -> child choice -> short resolution bridge -> Segment 2 -> calm coda`

The two generated segments are delivery parts of one complete 6-8 minute bedtime story.

A **series** is a chain of bedtime sessions over days/weeks/months with the same protagonist/world and durable memory.

Current MVP data still overloads `SeriesState.id` as the persisted story-session identifier and uses only technical episode numbers 1/2. Before public long-series rollout, persistence must separate:

- `series_id`: durable identity shared across many bedtime sessions;
- `session_id`: one bedtime story/night;
- `session_index`: 1, 2, 3... within the series;
- `segment_index`: 1 or 2 inside a bedtime session.

This separation is required before claiming support for a long-running serial.

## Memory scaling

The prompt must never grow with full story history.

Near-term active context:
- compact canon;
- relationship state;
- active arc;
- recurring characters;
- last summary;
- a small recent-choice window.

Long-series rule:
- durable state uses stable semantic keys;
- updates should refresh existing keys instead of creating synonyms;
- active context is recency/relevance bounded;
- old story prose remains archived outside the prompt.

Future retrieval may pull a small number of older relevant memories from persisted episode/choice history. Retrieval is an enhancement to compact canon, not a replacement for it.

## Rollout and rollback

During migration, the existing monolithic `index.ts` remains in the repository as a rollback baseline.

The split implementation uses `split-index.ts` in the same `story-generate` Edge Function and same production URL. Deployment therefore changes orchestration without creating a second public endpoint.

Rollout sequence:
1. typecheck and deterministic contract tests;
2. provider-free production smoke;
3. one controlled RU Episode 1 real-provider acceptance;
4. inspect published Luna output and stage metadata;
5. RU choice -> Episode 2 continuity acceptance;
6. repeat for UZ;
7. measure latency, provider calls, repair rate and semantic-safety rejection rate;
8. only then decide whether to enable a stronger Narrator escalation model.

## Success metrics before beta expansion

Track per generation:
- architect model and success/failure;
- narrator model actually used;
- deterministic validation errors;
- repair usage;
- escalation usage;
- provider call count;
- story/resolution word counts;
- semantic safety result;
- end-to-end latency;
- generation source.

The split architecture is successful when most stories publish from one Architect + one Luna Narrator without repair, branch state remains stable across continuation, and latency/cost remain acceptable for family use.
